# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	ch := make(chan int) // небуферизований канал

	wg.Add(1)
	go func() {
		// симуляція важкої роботи
		ch <- 42
		wg.Done()
	}()

	wg.Wait()
	fmt.Println(<-ch)
}
```

Оцінка промпту
Тепер промпт виконує вимоги завдання: код вставлено, є interleaving, wg.Wait() перед читанням і гарантованість дедлоку. Зауважень лише два:

Додайте повідомлення fatal error: all goroutines are asleep - deadlock!. ШІ відразу розумітиме, з якою помилкою має справу.
Питання «хіба не краще…» трохи підштовхує ШІ погодитися з вами. Фраза «якщо я помиляюсь, аргументуй» це вже частково врівноважує, тож проблема невелика.
Відповідь на промпт
Причина
Відправлення в небуферизований канал (ch <- 42) завершується лише тоді, коли інша горутина одночасно читає з цього каналу. Буфера немає, тому значенню нікуди «покластися».

Послідовність переплетення
main: wg.Add(1) збільшує лічильник до 1.
main: go func() створює горутину G і ставить її в чергу планувальника. Сама main не зупиняється.
main: wg.Wait(). Лічильник ≠ 0, тому main блокується в очікуванні wg.Done().
G: ch <- 42. Отримувача немає, тому G блокується на відправленні і до wg.Done() не доходить.
Обидві горутини заблоковані. Runtime бачить, що жодна горутина не може продовжити роботу, і завершує програму з fatal error: all goroutines are asleep - deadlock!.
Циклічне очікування
main чекає на wg.Done() від G.
G чекає, поки хтось прочитає з ch, а читати мала б main, але лише після wg.Wait().
Кожна сторона чекає на іншу. Це цикл, і ніхто з нього не вийде.

Чому порядок планування не має значення
Варіантів лише два:

G стартує раніше, ніж main дійде до wg.Wait(). G все одно заблокується на ch <- 42, бо <-ch у коді стоїть після wg.Wait(). Жодне переплетення не дає main прочитати з каналу раніше.
G стартує пізніше. Тоді main уже заблокована, і результат той самий.
Залежність закладена в порядку інструкцій, а не в таймінгах, тому дедлок гарантований.

Логіка виправлення
Я прибрав WaitGroup повністю:


ch := make(chan int)
go func() { ch <- 42 }()
return <-ch
Отримання <-ch саме по собі є точкою синхронізації. Воно блокує Run, доки G не надішле значення, і модель пам'яті Go гарантує happens-before між відправленням і отриманням. Чекати на G додатково немає чого: щойно значення передано, G завершується.

Альтернативи я відкинув з таких причин:

Прочитати <-ch до wg.Wait(). Це працює, але wg лишається зайвим кодом без жодної користі.
Буферизований канал make(chan int, 1). Це теж працює, але просто маскує неправильний порядок операцій замість того, щоб його виправити.
У версії, яку ви вставили в Run, був ще один баг: два читання з каналу, fmt.Println(<-ch) і return <-ch. Горутина надсилає лише одне значення, тож друге читання зависло б назавжди навіть після виправлення wg.

Канали проти WaitGroup: ви здебільшого праві
Канал передає дані й синхронізує горутини. WaitGroup лише чекає, поки N горутин завершаться, і нічого не повертає. Для одного значення WaitGroup дублює те, що канал уже робить, тому тут вона зайва.

Помилка у вашій тезі лише в тому, що ви сформулювали її як «різні сценарії». Ідіоматичний патерн fan-in поєднує обидва інструменти, коли продюсерів багато:


var wg sync.WaitGroup
for _, j := range jobs {
	wg.Add(1)
	go func() { defer wg.Done(); results <- process(j) }()
}
go func() { wg.Wait(); close(results) }() // хто закриє канал?
for r := range results { ... }
Тут канал передає результати, а WaitGroup визначає момент, коли всі продюсери закінчили роботу і канал можна закрити. Інакше range ніколи не завершиться. Зверніть увагу: wg.Wait() винесено в окрему горутину. Якби main спершу викликала wg.Wait(), а потім читала, виник би той самий дедлок. Якщо горутини повертають ще й помилки, ідіоматично використовувати errgroup.Group.

Що залишилося зробити
Локально -race не запускається: потрібен CGO_ENABLED=1 і gcc. Тести я прогнав без -race. У CI на Linux тести з -race запускатимуться.
Git на вашій машині перетворює переноси рядків на CRLF, тому локальний gofmt -l позначає всі файли як невідформатовані, навіть fixed_test.go. Під час коміту git зберігає файли з LF, тож у CI перевірка gofmt має пройти.
